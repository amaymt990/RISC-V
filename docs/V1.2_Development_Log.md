# Development Log — V1.2: Remaining RV32I Instructions + First Synthesis Pass

## Goal

Close the two remaining known ISA gaps from V1.1 (`SLTU`/`SLTIU`, `JALR`),
then get the design through a real synthesis tool for the first time —
not just simulated.

---

## SLTU / SLTIU

Added `SLTU` to the ALU (`(a < b) ? 1 : 0`, plain unsigned Verilog
comparison since `a`/`b` are already unsigned wires) and wired
`alu_control`'s `funct3 = 011` case to it, replacing the previous
"falls back to ADD, not implemented" placeholder.

## JALR

`JALR` (`rd = pc+4`, `pc = (rs1 + immediate) & ~1`) needed three real
changes, not just a control-unit case:

1. **`immediate_generator.v`** didn't recognize JALR's opcode at all —
   it uses the same I-type immediate encoding as `ADDI`/`LW`, but its
   opcode (`1100111`) wasn't in that case list, so it would have silently
   produced `immediate = 0`.
2. **A new `JALR` control bit**, threaded through `control_unit` →
   `id_stage` → `id_ex_register` → `ex_stage`, because JALR's jump target
   is fundamentally different from every other jump/branch: `(rs1 +
   immediate) & ~1`, not `(pc + immediate)`. Added a mux in `ex_stage.v`
   (and the equivalent in `cpu.v` for the single-cycle datapath) selecting
   between the two based on this bit.
3. Confirmed `Op1Sel` should stay at its default (`register`) for JALR,
   since — unlike `AUIPC`/`LUI` — JALR has a real `rs1` field; no operand
   override needed there.

Test: 9 instructions including a sentinel instruction planted at the
exact computed jump target (word 27, byte 108), to prove the CPU actually
lands where it should, not just that it doesn't crash. All 9 checks
passed first try.

Full regression suite (original hazard test, V1.1 test, single-cycle CPU,
new JALR test) — zero breakage, verified on both packaged Icarus Verilog
and iverilog-13.

## First Synthesis Pass

Installed Yosys (started with the Ubuntu-packaged 0.33, later moved to
`yowasp-yosys` 0.67 via pip after hitting a version-specific internal bug
in 0.33 — more on that below). Ran `synth -top cpu_pipeline` against the
full design.

This surfaced two real bugs that simulation never would have caught,
which is exactly the value of actually running a synthesis tool instead
of stopping at "the testbench passes":

### Bug 1 — `if (reset || flush)` breaks async/sync reset inference

`id_ex_register.v` combined its asynchronous reset and its synchronous
flush condition into one `if (reset || flush)` inside an `always @(posedge
clk or posedge reset)` block. This is completely valid Verilog and
simulates identically to writing them as two separate branches — but
Yosys's `proc_dff`/`proc_arst` passes, which need to cleanly separate
"this responds to the async edge on `reset`" from "this is a synchronous
condition that happens to be checked first," got confused by the `||` and
threw `ERROR: Multiple edge sensitive events found for this signal!` on
`pc_out`.

Diagnosed this by first suspecting a Yosys version bug (it also failed on
0.67, ruling that out), then testing the module in complete isolation
(failed there too, confirming it was a real RTL issue and not an
interaction with the rest of the design), then reading through the file
line by line and recognizing the OR-combined reset/flush pattern as a
known synthesis gotcha.

**Fix**: restructured to `if(reset) ... else if(flush) ...` — functionally
identical in simulation, but now synthesizes cleanly.

### Bug 2 — a zero-observable-output top module gets optimized to nothing

Even after fixing Bug 1, the "successful" synthesis produced an empty
`cpu_pipeline` module — just `clk` and `reset` ports, no logic at all.
Root cause: `cpu_pipeline`'s only ports genuinely *are* `clk` and `reset`
— everything else lives in internal register-file and pipeline-register
state. A synthesis tool has no way to know any of that state is meant to
be observed from outside, so its dead-code elimination correctly (if
unhelpfully) swept the entire design away as unreachable.

**Fix**: added `synthesis/cpu_pipeline_synth_top.v`, a synthesis-only
wrapper exposing four debug/monitor output ports (`dbg_pc`,
`dbg_wb_data`, `dbg_wb_rd`, `dbg_wb_regwrite`) wired to existing internal
signals. The real, simulation-verified `cpu_pipeline.v` is untouched —
this wrapper exists purely so the synthesis tool has *something*
observable to keep.

### Results

Full stats in `synthesis/SYNTHESIS_REPORT.md`. Headline numbers:

- **Whole design**: 36,107 cells / 9,689 flip-flops
- **Core CPU logic** (excluding `data_memory`, which synthesizes as
  8,192 individual flip-flops rather than a RAM macro without a target
  library that knows what block RAM looks like): **8,621 cells / 1,497
  flip-flops**

No Fmax/timing number yet — that needs a real target cell library (e.g.
sky130) and STA, which is a genuinely separate, larger effort (tried
fetching an sky130 liberty file directly, hit a 404 on the first
attempted path, decided against burning further time hunting for the
right repo — flagged as real future work instead of a quick add-on).
