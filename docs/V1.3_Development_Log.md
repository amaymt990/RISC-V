# Development Log — V1.3: Real Silicon-Grade Synthesis + STA (sky130)

## Goal

Move past generic synthesis (no target library, no real timing) to an
actual physical-design-grade result: real standard cells, real timing
data, a genuine Fmax number — the first item in the "OpenLane/Sky130 ASIC
Flow Exploration" line of the roadmap.

---

## The environment problem

Full OpenLane runs via Docker, orchestrating Yosys + OpenROAD + Magic +
Netgen + KLayout + OpenSTA together. No Docker available in this build
environment. Rather than treat that as a dead end, went looking for the
same underlying engines directly:

- **`pip install openroad`** — turned out to ship the real OpenROAD
  engine (not a stub): full Python bindings for floorplanning
  (`InitFloorplan`), placement (`Opendp`), clock tree synthesis
  (`TritonCts`), routing (`TritonRoute`, `GlobalRouter`), and a real
  embedded STA engine. ~600 MB, genuinely the whole tool.
- **The sky130 PDK** (real standard cells + LEF + liberty) — the
  standard way to get this is `volare enable`, which hit
  `403: API rate limit exceeded` on GitHub's REST API (a shared sandbox
  IP had already used up the unauthenticated hourly quota). Worked around
  it by downloading the exact same release assets directly via
  `github.com/efabless/volare/releases/download/...`, which redirects to
  `release-assets.githubusercontent.com` and isn't subject to the same
  per-request API limit. Same PDK, different download path.

One dead end worth noting: there's *also* a `sky130` package on PyPI,
but it's an unrelated GDSFactory/photonics toolkit, not the digital
standard-cell library. Wasted a few minutes there before finding the
right source.

## Synthesis against real sky130 cells

```
yosys: synth -top cpu_pipeline
       dfflibmap -liberty sky130_fd_sc_hd__tt_025C_1v80.lib
       abc -liberty sky130_fd_sc_hd__tt_025C_1v80.lib
```

21,215 real cell instances in the output netlist — confirmed by grepping
for actual sky130 cell names (`sky130_fd_sc_hd__nand2_1`,
`sky130_fd_sc_hd__dfrtp_1`, etc.), not generic placeholders. The
`dfrtp_1` (D-flip-flop) count came out to exactly 1,497 — matching the
generic-synthesis flip-flop count from the V1.2 report precisely, a good
sanity check that both synthesis paths agree.

## Real STA, via OpenROAD's Python API

```python
from openroad import Tech, Design
tech = Tech()
tech.readLef(tech_lef)
tech.readLef(cell_lef)
tech.readLiberty(liberty_file)
design = Design(tech)
design.evalTclString(f"read_verilog {netlist}")
design.evalTclString("link_design cpu_pipeline")
design.evalTclString("create_clock -name clk -period 300 [get_ports clk]")
design.evalTclString("report_checks -path_delay max")
```

21,215 instances linked. First result: **283.3 ns critical path (~3.5
MHz)** — much slower than expected. Traced it: the worst path's second
hop alone was 191.9 ns, a single buffer driving into `data_memory`'s
write-enable decoder. Root cause: `data_memory`'s 256-word array was
never mapped to a real SRAM macro (same issue flagged in the V1.2 generic
synthesis report), so it synthesized as 8,192 individual flip-flops, and
the write-enable signal fans out to all 8,192 of them from one decoder.

Rather than report that single number as "the" Fmax — which would be
technically true but misleading, since it says far more about an
unmapped memory model than about the processor — pulled a second, more
representative number: the worst path landing on the register file
(`ID/rf/*`), which doesn't touch `data_memory` at all.
**4.77 ns → ~210 MHz.** That's the more honest estimate of what this
pipeline's actual logic can do once memory is properly mapped.

Finding the register-file-specific path required first querying the
design's real instance names via the Python API
(`block.getInsts()` → `getName()`), since a first guess at the
hierarchical naming pattern (`*rf.registers*`) didn't match OpenROAD's
actual naming (`ID/rf/_10933_` etc, since gate-level synthesis replaces
the original array with individually-named flattened cells).

---

## Why report two numbers instead of picking one

A single "3.5 MHz" number undersells the design — it's an artifact of a
missing RAM macro, not a statement about the pipeline. A single "210 MHz"
number oversells it — it ignores a bottleneck that's genuinely still in
the current netlist. Reporting both, with the reasoning that connects
them, is what an honest timing summary of an unfinished physical design
actually looks like. Full writeup in
`synthesis/sky130/SYNTHESIS_REPORT_SKY130.md`.

## Next Steps

- Fix `data_memory`'s RAM mapping — the single highest-leverage next
  step, would likely make the two numbers above converge
- Real floorplanning (`InitFloorplan`) and placement (`Opendp`) for
  post-placement (not wire-load-estimated) parasitics
- Clock tree synthesis (`TritonCts`)
- Multi-corner STA (`ss`/`ff`, not just `tt`)
- Full routing (`TritonRoute`) for a final signoff-quality timing number
